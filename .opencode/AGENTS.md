# QA Multi-Agent System — Global Rules

## Общие принципы

### 1. Запрет на выдумывание результатов (No Hallucination)
- **СТРОГО ЗАПРЕЩЕНО** имитировать успешное выполнение Tool или Skill.
- Если Tool не доступен, вернул ошибку или результат не получен — **немедленно сообщить об этом**.
- Никогда не генерировать фиктивные ID задач, тест-кейсов или артефактов.
- Все результаты должны быть основаны **только** на реальных данных из внешних систем.

### 2. Правило 3 попыток (Retry Policy)
При временных ошибках (Timeout, Network Error, Rate Limit):
- Сделать **до 3 попыток** вызова Tool.
- Между попытками выдерживать паузу **не менее 200 мс**.
- Если после 3 попыток действие не выполнено — **остановить процесс** и сообщить причину.
- **НЕ повторять** при ошибках валидации, отсутствия прав доступа или некорректных параметрах.

### 3. Idempotency (Идемпотентность)
- Перед любой Write-операцией (создание задачи, тест-кейса) **проверить существование** аналогичной сущности.
- Использовать поиск по заголовку, описанию и связи с требованием.
- Найденные совпадения **не пересоздавать** — зафиксировать как "существующие" в аудит-логе.
- Если проверка невозможна (нет Tool для поиска) — **остановить этап** и сообщить причину.

### 4. Partial Failure (Частичный сбой)
- Если часть Workflow выполнена успешно, а следующий этап завершился ошибкой:
  - **Зафиксировать State**: что выполнено, какие ID получены, где возникла ошибка.
  - **НЕ объявлять весь процесс успешным**.
  - **НЕ выполнять автоматический Rollback** (удаление созданных данных может быть опаснее).
  - Сообщить пользователю частичный результат и причину остановки.

### 5. Human-in-the-Loop (HITL)
Агент должен **немедленно остановить работу и запросить решение человека** в случаях:
- Обнаружены критические неоднозначности или противоречия в требованиях.
- Отсутствует ключевая информация для продолжения.
- Tool недоступен после 3 попыток.
- Quality Gate не пройден и требуется экспертная оценка.
- Ситуация не описана в инструкции (неоднозначное поведение).
- Необходимо выполнить действие вне зоны ответственности агента.

При эскалации агент должен предоставить:
- Контекст: что произошло, на каком этапе.
- Какие данные известны.
- Какое решение требуется от человека.

### 6. Управление контекстом (Context Management)
- Загружать в контекст **только данные, необходимые для текущего решения**.
- Не использовать устаревшие, дублирующие или нерелевантные данные.
- При большом объёме данных — использовать фильтрацию, сохраняя бизнес-правила и ограничения.
- Не сохранять в контексте комментарии выполнения текущей задачи.

### 7. Аудит-лог (Audit Log)
Фиксировать каждое действие:
- Время, этап, инструмент.
- Действие (создан/пропущен/эскалирован/ошибка).
- ID артефакта, причина.
- **НЕ логировать** секреты, токены и пароли.

### 8. Artefact Storage
Все промежуточные артефакты хранить в папке `/artifacts/`:
- Requirement Review Artifact: `/artifacts/requirement-review.md`
- Jira Task Artifact: `/artifacts/jira-tasks.md`
- Test Model Artifact: `/artifacts/test-model.md`

Каждый этап использует Artifact как основной входной контекст. **Не использовать историю диалогов вместо Artifact.**

### 9. Ограничения объёма
- **Максимум тест-кейсов на одну функциональность:** 50 (при превышении — разбить и эскалировать).
- **Обработка пачками:** не более 100 артефактов за один вызов Tool.
- **Таймаут одного запроса:** 30 секунд.

### 10. Приоритизация
Приоритет вычисляется из критичности требования:
- 🔴 **Высокий:** критичность "высокая" или критичное бизнес-правило.
- 🟡 **Средний:** критичность "средняя".
- 🟢 **Низкий:** критичность "низкая".
- ⚪ **Не задан:** если критичность отсутствует — не выдумывать, зафиксировать и эскалировать.
