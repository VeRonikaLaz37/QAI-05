## 🎯 Назначение (Purpose)
Skill выполняет систематическое ревью требований и формирует проверенный **Requirement Review Artifact**, который используется следующими этапами Agent Workflow.

> ⚠️ **Важно:** Skill отвечает *только* за анализ требований. Он не проектирует Jira-задачи, не создает тестовую модель и не выполняет действия во внешних системах.

## 📥 Входные данные (Inputs)

### Обязательные:
- Актуальные требования текущей функциональности, полученные агентом из Confluence.
- Ссылка, идентификатор или иной reference на исходный источник требований.

### Опциональные:
- Критерии приёмки (Acceptance Criteria).
- Связанные бизнес-правила и ограничения.
- Релевантная связанная документация.
- Подтверждённые проектные соглашения.
- Дополнительный Context, явно предоставленный агентом.

## 🧠 Управление контекстом (Context Management)
- Использовать **только** данные, относящиеся к анализируемой функциональности.
- Не использовать устаревшие версии требований, если доступна более актуальная версия.
- Не использовать предыдущие выводы агента как Source of Truth, если их можно проверить по исходным требованиям.
- При большом объёме документации анализировать только релевантные фрагменты, переданные агентом.
- **Не загружать и не запрашивать самостоятельно** данные из Jira или Qase: внешние Tools управляются Agent Instruction.
- Если входного Context недостаточно — явно зафиксировать **Missing Information**.

## 📋 Процедура (Procedure)
Выполняй шаги последовательно:

1. Определи **Scope** анализируемой функциональности.
2. Выдели явно сформулированные **функциональные требования**.
3. Выдели **бизнес-правила** и **ограничения**.
4. Выдели **Acceptance Criteria**, если они явно определены.
5. Определи **зависимости** между требованиями и связанными функциями.
6. Найди **неоднозначные формулировки**, допускающие несколько интерпретаций.
7. Найди **внутренние противоречия** между требованиями.
8. Определи **отсутствующую информацию**, необходимую для однозначного понимания ожидаемого поведения.
9. Выдели **правила валидации** и значимые **граничные условия**, если они следуют из требований.
10. Определи основные **Positive Flows** и **Negative Flows**, которые прямо следуют из требований.
11. Определи **QA-риски**, связанные с требованиями.
12. Сформируй **Open Questions** для спорных и неполных требований.
13. Сформируй структурированный **Requirement Review Artifact**.

## 🚫 Правила (Rules)

### Обязательные:
- **Не придумывать** отсутствующие требования, бизнес-правила, ограничения или Acceptance Criteria.
- **Не выдавать** предположение за подтверждённое требование.
- **Не разрешать** бизнес-неоднозначности самостоятельно.
- Если два авторитетных фрагмента противоречат друг другу — зафиксировать **Conflict**.
- Каждый существенный вывод должен иметь связь с исходным требованием или source reference (если это возможно).

### Строгие запреты:
- ❌ Не создавать Jira-задачи.
- ❌ Не создавать тест-кейсы и тестовую модель.
- ❌ Не изменять исходные требования.
- ❌ Risk или Recommendation **не должны подменять** исходное Requirement.

## 🧩 Паттерны рассуждений (Reasoning Pattern)

### 🔁 Self-Refine / Critic
После формирования первого варианта Requirement Review проверь его по **Completion Criteria**. Если обнаружены исправимые недостатки — уточни Artifact и выполни повторную проверку.

> ⚠️ Максимальное количество циклов исправления определяется Agent Instruction. Skill не должен инициировать бесконечное самоуточнение.

### 🌳 Branching / Tree
Не применяется по умолчанию. Если требование допускает несколько существенно разных трактовок, Skill **не выбирает одну ветвь**, а фиксирует **Ambiguity** и варианты трактовки для эскалации.

## 📤 Выходные данные (Output)

Создай **Requirement Review Artifact** со следующей структурой:

### 📑 Структура артефакта

| # | Раздел | Описание содержимого |
|---|---|---|
| 1 | **Scope** | Границы анализируемой функциональности, контекст и область применения |
| 2 | **Requirements** | Явно сформулированные функциональные требования (FR) |
| 3 | **Business Rules** | Бизнес-правила, регулирующие поведение системы |
| 4 | **Acceptance Criteria** | Критерии приёмки, если они явно определены в источнике |
| 5 | **Validation Rules** | Правила валидации данных и значимые граничные условия |
| 6 | **Dependencies** | Зависимости между требованиями и связанными функциями/системами |
| 7 | **Ambiguities** | Неоднозначные формулировки, допускающие несколько интерпретаций |
| 8 | **Missing Information** | Отсутствующая информация, необходимая для однозначного понимания |
| 9 | **Conflicts** | Внутренние противоречия между требованиями или источниками |
| 10 | **Positive Flows** | Основные позитивные сценарии, прямо следующие из требований |
| 11 | **Negative Flows** | Негативные/альтернативные сценарии, прямо следующие из требований |
| 12 | **Boundaries** | Граничные условия и ограничения функциональности |
| 13 | **Risks** | QA-риски, связанные с требованиями |
| 14 | **Open Questions** | Вопросы для Product Owner / Lead QA по спорным и неполным требованиям |
| 15 | **Source References** | Ссылки на исходные требования и документы-источники |

## 📜 Контракт артефакта (Artifact Contract)

| Поле | Значение |
|---|---|
| **Producer** | Skill `requirement-review` |
| **Consumers** | Skill `task-design`, Skill `test-design` |
| **Artifact** | Requirement Review |
| **Validation** | Completion Criteria этого Skill |
| **Error Handling** | Если обязательный вход отсутствует или критическая неоднозначность не позволяет сформировать надёжный Artifact — вернуть **невалидный/заблокированный результат** с описанием причины, а не заполнять пробелы предположениями |

## ⚠️ Обработка ошибок (Error Handling)
- Если обязательный вход отсутствует → вернуть заблокированный результат.
- Если критическая неоднозначность не позволяет сформировать надёжный Artifact → вернуть заблокированный результат с описанием причины.
- **Никогда не заполнять пробелы предположениями.**

## ✅ Критерии завершения (Completion Criteria)

### Базовые требования:
- [ ] Все предоставленные релевантные требования проанализированы.
- [ ] Явные **Requirements**, **Business Rules** и **Acceptance Criteria** выделены.
- [ ] **Ambiguities** и **Conflicts** либо зафиксированы, либо явно указано, что они не обнаружены.
- [ ] **Missing Information** зафиксирована.
- [ ] **Validation Rules** и значимые **Boundaries** отражены там, где они следуют из требований.
- [ ] **Positive** и **Negative Flows** определены в пределах доступных требований.
- [ ] **QA Risks** и **Open Questions** зафиксированы.
- [ ] Существенные выводы имеют **Source References** (если source reference доступен).

### Финальная проверка:
- [ ] Artifact **не содержит придуманных требований**.
- [ ] Artifact прошёл самопроверку по Completion Criteria (Self-Refine).
