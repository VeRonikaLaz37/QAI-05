## 🎯 Назначение (Purpose)
Skill проектирует **риск-ориентированную тестовую модель** на основании проверенного Requirement Review и формирует **Test Model Artifact**, пригодный для последующего создания тестовых сущностей через Qase Tool.

> ⚠️ **Важно:** Skill проектирует тесты. Он не выполняет тестирование и не создаёт сущности в Qase напрямую.

## 📥 Входные данные (Inputs)

### Обязательные:
- Валидный Requirement Review Artifact

### Опциональные:
- Ограничения тестирования
- Релевантные существующие тест-кейсы, если агент получил их через Qase Tool
- Проектные правила приоритизации
- Дополнительный Context, явно переданный агентом

## 🧠 Управление контекстом (Context Management)
- Использовать Requirement Review как основной вход для тест-дизайна
- Не анализировать заново весь Confluence, если необходимая информация уже представлена в проверенном Requirement Review
- Использовать существующие тест-кейсы Qase **только** для анализа текущего покрытия и предотвращения дублирования
- Не загружать в Context всю тестовую модель Qase, если достаточно релевантных тестов текущей функциональности
- **Не вызывать Qase Tool самостоятельно**: Tool-вызовы выполняются агентом

## 📋 Процедура (Procedure)
Выполняй шаги последовательно:

1. Определи тестируемые функции и бизнес-правила из Requirement Review
2. Оцени риски и бизнес-критичность
3. Определи **Positive Scenarios**
4. Определи **Negative Scenarios**
5. Покрой **Validation Rules**
6. Покрой значимые **Boundary Conditions**
7. Добавь важные альтернативные потоки и зависимости
8. Используй **risk-based подход** для дополнительного покрытия рисков
9. Для каждого сценария сформулируй проверяемый **Expected Result**
10. Назначь **Priority** на основании риска и критичности
11. Сохрани **Traceability** к Source Requirement
12. Сравни с переданными существующими тестами и исключи необоснованные дубли
13. Сформируй **Test Model Artifact**
14. Проверь Artifact по **Completion Criteria**

## 🚫 Правила (Rules)
- ❌ Не придумывать бизнес-поведение, которого нет в Requirement Review
- ⚠️ Допускаются **risk-based проверки**, не описанные дословно в требованиях, но они должны быть явно обозначены как **QA/Risk-based**, а не как бизнес-требование
- ❌ Каждый сценарий должен иметь понятную цель и проверяемый Expected Result
- ❌ Не создавать несколько сценариев, проверяющих одно и то же без дополнительной ценности
- ❌ Не скрывать нерешённые Ambiguities и Conflicts
- ❌ Не вызывать Qase Tool
- ❌ Не считать Test Model фактически созданной в Qase до подтверждения Tool на уровне агента

## 🧩 Паттерны рассуждений (Reasoning Patterns)

### 🔁 Self-Refine / Critic
Основной паттерн для проверки качества Test Model: **Generate → Evaluate → Improve → Evaluate**.

Проверяй:
- Полноту покрытия
- Негативные сценарии
- Границы
- Ожидаемые результаты
- Приоритеты
- Трассировку
- Дубли

### 🌳 Branching / Tree
Не применяется по умолчанию. Используй **только** если есть несколько существенно разных тестовых стратегий или вариантов покрытия, влияющих на риск, стоимость или время.

- Сравни **не более трёх вариантов**
- Выбери наиболее обоснованный

### 👁️ Reviewer
Если Agent Workflow включает независимый Reviewer для критической Test Model:
- Передай ему валидный **Test Model Artifact** и необходимые исходные ссылки
- **Не передавай** полную историю работы Skill

## 📤 Выходные данные (Output)

Создай **Test Model Artifact**. Для каждого тестового сценария укажи:

| Поле | Описание |
|---|---|
| **Local ID** | Временный идентификатор сценария |
| **Title** | Название тестового сценария |
| **Source Requirement** | Ссылка на исходное требование |
| **Priority** | Приоритет сценария |
| **Type** | Тип сценария |
| **Preconditions** | Предусловия (если применимо) |
| **Steps / Test Intent** | Шаги выполнения или описание намерения теста |
| **Expected Result** | Ожидаемый результат |
| **Risk Reference** | Ссылка на риск (если сценарий risk-based) |
| **Open Question / Blocker** | Если сценарий зависит от нерешённой неоднозначности |

### 📌 Допустимые значения

**Priority** (если проектом не определён другой контракт):
- `HIGH`
- `MEDIUM`
- `LOW`

**Type** (базовые, если проектом не определён другой контракт):
- `positive`
- `negative`
- `boundary`
- `risk-based`

## 📜 Контракт артефакта (Artifact Contract)

| Поле | Значение |
|---|---|
| **Producer** | Skill `test-design` |
| **Consumer** | Agent, этап создания тестовых сущностей через Qase Tool |
| **Artifact** | Test Model |
| **Validation** | Completion Criteria этого Skill |

### 🚨 Error Handling
Еcли критическая часть требований неоднозначна, не выдумывай Expected Result; пометь зависимые сценарии как BLOCKED/REQUIRES_HUMAN_DECISION или исключи их из готовой к созданию части Artifact с явным объяснением.

## ✅ Критерии завершения (Completion Criteria)

- [ ] критические подтвержденные требования имеют тестовое покрытие
- [ ] Positive Scenarios покрыты
- [ ] релевантные Negative Scenarios покрыты
- [ ] Validation Rules покрыты
- [ ] значимые Boundary Conditions покрыты
- [ ] Expected Result определён для каждого готового сценария
- [ ] Priority назначен или явно отмечено, что он требует внешнего решения
- [ ] Traceability к требованиям сохранена
- [ ] risk-based сценарии отделены от бизнес-требований
- [ ] необоснованные дубликаты отсутствуют
- [ ] нерешённые Ambiguities и Blockers видимы
- [ ] Artifact готов к передаче агенту для создания тестовых сущностей через Qase Tool
